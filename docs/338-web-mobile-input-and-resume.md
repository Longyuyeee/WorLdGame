## 从使用障碍到修复

| 使用场景 | 旧实现的实际问题 | 处理 |
| --- | --- | --- |
| 作者刚开始中文组合输入，尚未触发文本变化 | Ctrl+Enter 冒泡到全局后插入新语句；候选按键也可能打开演出对话框 | 输入框组合中停止快捷键冒泡；全局插入/演出处理同时识别 isComposing 和兼容 keyCode=229，不阻止正常输入法默认行为 |
| 素材名称输入/取消候选 | 全局 Escape 可能关闭整份素材弹窗 | 素材/备份关闭快捷键忽略组合输入；普通 Escape 行为保持 |
| 玩家使用中文输入法或同页可编辑区 | Enter/空格可能推进剧情，组合中的 Escape 会关闭菜单 | 在全局处理前过滤已处理事件、组合输入/229；推进排除 contenteditable，既有输入框/按钮保护保留 |
| 切走页面或宿主暂停时最后一次点按 | 仅部分按钮和键盘/Auto 有暂停保护，直接点按仍能改剧情状态 | 所有剧情 intent 入口以最新宿主 activity 拦截，包括已排队回调，不只隐藏按钮 |
| 浏览器导航/历史缓存与冻结事件交错 | 只有 visibility/freeze/resume，没有 pagehide/pageshow；一种恢复事件可能过早解除另一种暂停 | 增加同步页面离开/返回状态；可见性、页面离开、freeze 和外部宿主分别作为暂停上限，各自恢复不越权；Auto 回来重新等待，不补跑后台时间 |

四项新增回归先在旧实现失败，修复后通过；再补独立暂停上限、素材 Escape 和真实 Auto 时钟三项。输入组合时只屏蔽应用快捷键，不统一阻止浏览器编辑事件；Ctrl/Cmd+S 仍沿既有保护阻止浏览器另存，不提交半成品。

### 不混淆的测试证据

- 旧 1.7.0 独立 HTML 的三引擎基线均复现组合 Enter 误推进、显式 pagehide 未暂停；这两项是派发的边界事件，不是手机输入法候选实录。
- Chromium 使用协议执行组合输入，start/input 为 trusted，结束事件为 untrusted（在独立原生 textarea 中同样复现）。保留原始事件标记，验证中文提交、旋转与保存，但**不声明操作系统中文键盘/候选窗已验收**。Firefox/WebKit 使用显式组合边界和真实文本修改，没有冒充 OS IME。
- 真实 HTTP 离开/返回不等于必然命中 BFCache。记录 pagehide 的 trusted/persisted 及播放器是否保留：非缓存离开时，既有导出启动器会先卸载播放器、回收音轨；保留到缓存时才应看到宿主 suspended。不能在正常卸载后强行查不存在的 main，把正确清理误判为产品故障。返回后若页面重建，通过已保存槽位显式恢复，不声称保持了内存文档。
- headless Chromium 接受协议冻结指令，但本机未发出 freeze/resume，独立页面尝试同样无事件。报告将 `acceptedAsNativeCoverage` 保持 false；实际冻结/锁屏未据此通过。显式 pagehide/pageshow/freeze 交错和 Auto 时钟由浏览器边界与回归测试覆盖，不代替真机系统生命周期。
- 触控由桌面引擎自动化触摸/布局模拟，WebKit 不是 iPhone Safari，Firefox 的窄屏不是 Android Firefox 真机。以上三引擎结果只说明本机该版本的这组任务，不能推导“所有主流手机均已支持”。
