## 完整输入与校验边界

之前只编码推进／读取的结果，发送给线程的完整历史仍重复携带各检查点的三个进度列表。[输入传输](../apps/player-shell/src/session-input-transport.ts)现在对至少 480 条历史的普通异步推进、前台保存和后台恢复编码；接收线程先展开完整数据，再逐次执行原公开 Core 推进或序列化。读取的输入、压力保护、短历史、回想和无 Worker 的兼容路径保持原计算边界，Auto／Skip 的推进也没有扩大到异步。

输入和原结果复用[同一列表编解码器](../apps/player-shell/src/history-list-transport.ts)，但包版本分别识别。每个包独立包含完整检查点表，前后段引用只限本包，不从旧状态补数据。当前 Runtime 与其检查点、同包候选间的实际对象共享保持；历史正文、记录未来、归档、回想入口、编译数据与全部保存候选不截短。线程池不缓存源、结果或“已校验”结论，取消后新线程也不依赖上次请求。

错误版本、稀疏数组、非法索引、列表边界、候选和过量展开均拒绝，不把坏包当普通源再试。沿用 Runtime 的列表／表数量上限与单包八百万个 ID 引用单元预算；编码超预算返回完整普通传输，不新增 Runtime 容量限制。审计补上合并表超量的保护：多个候选可以含值相同但并不共享的检查点，发送端必须退回完整普通包，不能生成接收端会拒绝的表。预算形状测试不算有效剧情或设备容量验收。

后台慢复制避让仍计入输入准备和发送，不只看原生 postMessage；显式保存不延后到另一段。五秒超时、原错误说明、明确兼容模式、菜单／暂停／切换取消、最多两个计算通道和迟到结果保护保持。不改 Canonical、Runtime、存档格式、数据库或旧档兼容规则，不在 Worker 操作物理媒体。

## 本机串行比较

下表为每档三次的中位数，单位 ms，均为“基线 → 当前”。发送列只统计原生 postMessage 同步阻塞；工具推进总等待包含输入准备、计算、交互观察和帧回调，推进至恢复落盘还包含存储与轮询。

| 夹具与历史条数 | 推进发送 | 工具推进总等待 | 推进至恢复落盘 |
| --- | --- | --- | --- |
| 文字 480 | 6.2 → 2.5 | 128.8 → 129.3 | 257.6 → 208.2 |
| 文字 960 | 22.6 → 3.7 | 252.4 → 195.9 | 676.1 → 565.2 |
| 混合 480 | 6.7 → 2.7 | 129.2 → 126.3 | 265.8 → 230.7 |
| 混合 960 | 19.0 → 5.9 | 231.3 → 194.7 | 709.8 → 616.0 |

960 条的后台恢复发送，文字 21.6→2.7ms、混合 18.9→3.5ms；正文首次观察到的帧回调分别 213.6→160.3ms、196.6→160.8ms。十二次长历史普通推进没有 ≥50ms 主线程长任务，基线也没有，不重复计算为本批收益。真实输入包均检查传输标识及至少 count+1 个检查点，不用只有标识的空包代替完整历史。

收益主要出现在 960 条样本；480 条文字的总推进未改善。960 条快速保存文字 527.7→512.5ms、混合 543.9→528.9ms；快速读取文字 681.6→656.6ms、混合 694.6→728.6ms。读取输入未启用本次编码，部分读取更慢，不能宣称所有操作都提速。120 条仍走原路径，其推进文字 67.2→57.8ms、混合 59.2→70.4ms 的差异不归功于本批。固定先旧后新、每档仅三次的本机样本不代表总体性能、整体 CPU 降低或手机达标。

十八对快速槽规范字节数／SHA、Session artifact hash、Runtime hash、正文、游标与完整历史长度逐项一致。压力保护先完整落盘再缩小内存窗口，刷新后显式恢复返回完整 960 条，原快速槽不变；两组计算通道峰值 2，保护与卸载后归零。混合组真实图片与音轨身份、自然结束和冷恢复保持，页面／媒体错误为空；小尺寸夹具不代表大素材、视频或人工听感。最终重新构建四组主线程／子 Worker 及夹具、冻结源、CSS 摘要全部匹配采样报告。

证据分为 [纯文字](../evidence/web-session-input-transport/text/current.json)和[背景／双立绘／音乐／有限语音](../evidence/web-session-input-transport/mixed/current.json)。基线固定 `09440cf9782810c15be9f2e83840192198771ed5` 的 Runtime／Shell 源，主线程与子 Worker 都使用冻结源；每组自然推进到 120／480／960 条，再各做三轮快速保存、继续一句、读取。新旧原生 Worker 与 IndexedDB 串行运行，采样不与回归或其他浏览器任务并行。

原生 postMessage 同步耗时不包括在它之前的列表编码，也不等于整体复制成本。正文帧回调不是物理呈现；推进、读取和落盘总等待分别记录，不能把编码后的 JSON 体积或主线程 CPU 采样当作实际复制字节、整体 CPU 或手机达标。120 条不启用编码，其变化不归功于本批。报告 head 是采样时的基底，最终代码由本批提交与可重建 bundle 摘要定位。
