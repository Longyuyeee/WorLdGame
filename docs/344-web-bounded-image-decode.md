# 受限图片解码与 1.7.5 候选 · 2026-10-16

接续 `fca1b02` / [#343](343-web-background-recovery-and-candidate.md)，继续 [#304](304-web-complete-gal-delivery.md) 的实际 Web 连续运行问题。本批不改变作品画幅、剧情或素材，不增加原生平台功能，也不绕过保存和资源保护换取速度。

## 用户问题与实际改动

上一批恢复保存转到线程后，完整路线主线程采样仍有约 238 ms 的 `createImageBitmap` self 时间。读取实际代码发现，普通 PNG 先经头部预检、加载为 Image，再从 Image 创建 Bitmap；后者在本机有明显主线程开销。

- 可用环境改为一次受限 fetch，核对实际 PNG 头部、尺寸和每个流块后，直接以 Blob 创建可关闭的 Bitmap，仍绘入同一 1:1 Canvas。不再先加载 Image 再快照。无需新增网络 Worker、永久图片缓存或改变作者构图。
- 单文件编码上限 32 MiB、像素上限 4,194,304、共享 64 MiB 预算保持。头部确认就预留像素峰值；编码暂存块和 Blob 副本也在复制之前计入同一共享预算，不只计算最终 Canvas。响应没有 Content-Length 或谎报更小也不能无限读取；206 片段不冒充完整源。
- 不支持 fetch/Bitmap、文件或 CORS 限制、非 PNG 保留原先受检查的 Image 兼容路径。已完成的 Blob Bitmap 拒绝才允许兼容回退，重新核对实际尺寸；超限、取消、超时不进入无预算紧急图片。Bitmap 尺寸不符明确拒绝并关闭，不再把它当普通不支持错误。
- 5 秒物理解码期限、15 秒组件加载期限和原画面重试入口保持。不可取消的物理解码仍保留像素及编码计账，阻止重试风暴；迟到结果只关闭、不绘制，实际完成后才解除隔离。成功绘制关闭 Bitmap，离开场景/回标题释放 Canvas；不把 JS 计账当成浏览器物理内存实测。
- 审计补到一个保护边界：reader/body 清理拒绝可能把原本的预算错误替换成普通 IO 错误，进而走错误的回退分类。新增测试先明确失败，再修正为清理不遮盖原结果；完整读取与原头部预检均保留政策错误/取消身份。

保存格式、History 校验、独立恢复 Worker 与正式手动/快速/自动槽位没有改动；本批不声称它们都在后台，也没有删除历史来减少工作量。

## 真实像素与资源对照

使用 1.7.4 包内全部 **13 张 PNG**，逐一比较 HTTP、Blob、data 三种来源，在 Chromium / Firefox / Windows WebKit 共 **117 组**。旧实现从固定 `fca1b02` 的实际 `native-atlas.ts` 构建，不用当前兼容分支假装旧代码；新旧模块分别拥有自己的资源计账。

每组读取实际 Canvas RGBA 并比较尺寸和 SHA-256，验证透明像素、色彩及采样未变，再释放并核对两边持有量/物理解码为零。三个引擎的新路径均实际为 `owned-blob-bitmap`，不是只测了回退。新包 PNG 字节另与这批原素材摘要相等。报告 `image-parity.json` 固定旧提交、当前三个源码的 LF 规范化摘要和原包身份，换机可重跑；不是跨浏览器要求像素摘要彼此相同。

首个探针打包遇到 Vite 返回数组而非单个输出，修正工具后重新执行，不当产品成功。图片超限、暂停、清理分类及资源计账的修正后均重新验证，不用前一次运行时的测量或导出替代最终代码。
