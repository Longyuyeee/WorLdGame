## 读档路径与校验边界

正式 Player 的读取路径是 Shell 的前台任务、原生 Worker、PlayerCore 和 Runtime Session Save。原路径完整校验规范字节、历史链、身份和摘要后，合并当前已读与收集进度又通过公开 History 入口重新扫描整条链；旧 v1 存档在规范化后还重复扫描一次。

现在只在同一次同步读取内部复用已经成立的校验前提。v2 完整历史扫描一次；v1 先检查原 v1 摘要和完整旧链，再补空归档并转换版本，不重复扫描仅替换版本字段的同一链。当前进度仍独立检查项目、作用域、排序、唯一性和数量限制；只在有新增进度时重建当前检查点与相邻链接。

读取仍从原字符串重新解析，严格检查规范 JSON、尺寸、项目与构建、游标、每个检查点和 entry、归档、输入 tombstone 及原始摘要。公开 History 合并、后续读取与保存仍自行完整校验。没有跨调用的对象、字节或摘要缓存、持久信任标志、异步窗口或宿主回调，也没有裁剪历史、取消归档、放松损坏输入、改写规范字节或更换哈希算法。可执行 getter／proxy 不是既有纯数据存档契约。

内部续接函数不进入 Runtime 包入口；架构门禁只允许 History 与 Session Save 模块引用。Worker 传输、线程池、超时／取消、保存队列、先保护落盘再缩小内存窗口的规则均保持，不能把本次改动称为复制协议优化。

同一次保存／读取还只生成一次整份历史的规范文本与 UTF-8 字节，用于原 History 域摘要和封装。封装沿用封闭且已排序的十个字段，其他字段仍逐项使用既有规范序列化器；读取先检查确切字段，再将完整规范封装与原字符串比较，不直接截取或信任输入片段。非封装输入仍走原通用规范检查。v1 的原历史与规范化后 v2 历史是不同值，后者的摘要仍独立生成。

History v1／v2 域常量集中在既有内部字节模块，公开 Hash API 仍先生成规范字节。N52-E5b 门禁按实际位置核对域、公开入口、v1 摘要先于规范化，以及完整封装比较；未取消旧格式、摘要或损坏输入检查。新增测试用独立通用序列化和 Node SHA 验证原字节，并拒绝重复键、不同字段顺序、替代数字／转义、未知成员和错误历史类型。

## 基线与实测方法

新证据位于 `evidence/web-session-cost`，不覆盖 #353。基线冻结 8207650 的 Runtime 生产源，前台和子 Worker 使用同一覆盖；其他实际 Player 源未改动。`baseline-sources.json` 保留源文本，各报告记录精确 bundle、CSS 和夹具摘要，支持重新核对，不能把之后的工作区当作旧基线。

使用正式样式和同一 960 段文字夹具，由真实按钮依次读到 120、480、960 条，各重复三轮快速保存、推进、快速读取。读档合并已读标记后继续下一轮；基线与修复版逐轮比较完整状态 hash、正文、游标、历史长度及实际 IndexedDB 快速槽的规范字节数／摘要和 Session artifact hash。记录主线程长任务、心跳、发送消息的同步时间及响应到达；发送时间不代表完整复制，往返也包含排队、验证和传输。仅普通推进开启 CPU 采样，保存／读取不带 CPU 采样。

压力测试使用公开宿主通知，不代表物理低内存。实际先保护全部 960 条，再在内存中保留 64 条回退窗口；刷新后显式“恢复上次进度”应恢复原 960 条，不能拿内存窗口长度作为落盘恢复预期。首版脚本的这一错误断言保留在 `baseline-failure.*`，修正的是测例假设，不是保护策略。

960 条读取本次约减少 15%，120／480 条读取基本无变化，120 条保存略慢；保存总体改善很小，不作整体性能承诺。当前 960 条推进仍有 99、122、111ms 主线程长任务，CPU 采样中仍可见 SHA、规范编码和 `postMessage`，下一批继续处理，不记为整体流畅性通过。仅去重验证的中间版 960 条读取约 727ms，保留在 `validation-only.json`，不是最终代码结果。

九个对应存档点的规范字节数／SHA、Session artifact hash、状态、正文、游标和完整长度全部与基线一致；960 条最终快速槽为 6,427,956 字节。保护后的内存窗口为 64，显式冷恢复精确返回 960 条及原 hash，快速槽不变。两组序列化线程并发峰值均为 2，保护后和实际卸载后存活为 0，页面错误为空。两个报告的精确 bundle／CSS／夹具身份已重新构建核验；这是一台桌面 Chromium 151 上的串行文字样本，非统计性能、真实长篇媒体／物理手机或长期内存结论。
