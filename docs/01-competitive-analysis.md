# 竞品分析

## 1. 结论先行

市场上的工具大致分成五条路线：

1. **完整引擎型**：Naninovel、Utage、Ren'Py。运行时完整，但通常依赖 Unity 或桌面环境。
2. **可视化制作器型**：WebGAL Terre、LetsGal Studio、Visual Novel Maker、TyranoBuilder。入门直观，但纯节点/命令列表在超大项目中容易失控。
3. **叙事中间件型**：Yarn Spinner、ink。语言和调试优秀，但不负责完整 Gal 演出与发布。
4. **超文本图谱型**：Twine。路线可视化清晰、Web 发布简单，但视觉小说生产系统不完整。
5. **跨设备通用编辑器型**：GDevelop、Construct。不是 Gal 专用，却验证了移动编辑、云存储和云构建的产品路径。

没有一个现有产品同时做好以下四件事：

- 大型剧本的文本可维护性；
- 零代码演出的可视化可编辑性；
- 手机端完整创作；
- 从任意设备发起多平台构建。

这四项的交集就是 WorLd Studio 的首要市场机会。

## 3. 核心竞品详析

### 3.1 Naninovel

#### 已确认能力

- 以可读的 \`.nani\` 文本为基础，既能在文本编辑器中写，也能在 Story Editor 中逐行编辑。
- Story Editor 同时提供文件浏览、Inspector、场景行编辑和故事图。
- 故事图默认以脚本/目录为节点，进入脚本后才显示标签与内容，天然形成两级结构。
- 当前播放行可高亮，编辑能反映到游戏预览。
- 提供撤销/重做、Dirty Save、全局搜索、自动更新跳转引用。
- 内建保存/读取、回滚、本地化、UI、角色、音频等视觉小说系统。
- 服务化运行时允许替换系统或添加自定义命令。

#### 值得吸收

1. **文本必须是可独立维护的一级能力**，不能只是可视化编辑器的内部导出物。
2. **全局路线与场景内部结构分层**，避免巨型节点图。
3. **编辑器必须理解运行位置**，提供“跳到当前语句”和热刷新。
4. **重命名需要语义级引用更新**，不能依赖字符串搜索替换。
5. **可视化编辑和脚本扩展共用同一命令描述**，插件注册后应自动生成属性面板和补全。

#### 不应照搬

- 将完整生产流程绑定 Unity，会让手机端编辑、轻量安装和独立升级受限。
- “能在浏览器打开 Story Editor”不等于手机上的完整创作体验。
- 对新手而言，Unity 工程、资源导入和组件系统仍有较高认知负担。

### 3.2 Utage / 宴

#### 已确认能力

- Excel 表格是主要剧本入口，写角色名和台词即可生成内容。
- 资源、角色、声音、动画、口型、眨眼、层级和本地化均有配置表。
- 多语言可通过增加表格列完成。
- 支持 Live2D、3D 对象、下载章节、CG/场景回想、音乐室、全屏文本、Ruby 和日文禁则。
- Unity C# 源码完整开放在项目内，便于深度定制。
- 支持导入校验、文本溢出检查、增量导入与日志。

#### 值得吸收

1. **为批量生产提供表格视图**：台词、配音、翻译状态和资源映射需要批量编辑。
2. **本地化是内容模型的一部分**，不是上线前临时导出。
3. **日式排版细节是行业基线**：Ruby、禁则、全屏 NVL、多个消息窗口不能遗漏。
4. **章节资源分包与远程下载**适用于长篇、连载和移动端体积管理。
5. **导入前验证**比运行时报错更重要。

#### 不应照搬

- 不能把 Excel 变成唯一真源。合并冲突、引用重构、复杂条件和演出可读性都会下降。
- 保存外部表格后再导入的循环会打断即时反馈。
- UI 深度定制仍依赖 Unity Prefab/组件知识。

### 3.3 Yarn Spinner

#### 已确认能力

- 以人类可读脚本表示节点、选项、变量、命令和条件。
- VS Code 提供语法高亮、补全、图谱、预览和调试。
- 浏览器工具可立即编写、运行、分享，且支持现代浏览器和平板。
- Story Solver 面向软锁、不可达或错误状态做叙事验证。
- 使用稳定 Line ID 关联翻译文本和配音资产。
- 官方集成覆盖 Unity，并扩展到 Godot、Unreal；表现层由 Dialogue Views/宿主引擎承担。

#### 值得吸收

1. **叙事语言、编译器、运行时和表现层分离**。
2. **稳定文本 ID**是翻译、配音、历史记录、修改追踪和分析的基础。
3. **编辑器级调试器**需要断点、变量观察、跳转和调用栈，而不只是 Play。
4. **路线求解器**应在发布前自动探索状态空间。
5. **浏览器零安装沙盒**是教学、评审和分享的高价值入口。

#### 不应照搬

- WorLd Studio 不能只做对话中间件；必须提供完整可发布的视觉小说运行时。
- 完整生产工作流不能强制用户安装 VS Code。

### 3.4 WebGAL / WebGAL Terre

#### 已确认能力

- Web-first 运行时，脚本覆盖对白、背景、立绘、音频、视频、分支、变量、动画和特效。
- Terre 编辑器集成项目创建、素材管理、多标签脚本、实时预览和发布。
- 编辑器前端、后端、Electron 壳和游戏 Electron 包装分别组织，支持自定义引擎模板。
- 可导出 Web 和 Windows；官方文档提供 Android 工程导出流程。
- 2026 年版本加入实验性流程图，并持续改善预览拖拽和 Android 运行环境。
- MPL-2.0 开源，可商业使用但需遵守许可边界。

#### 值得吸收

1. **Web 运行时作为最小公分母**可显著降低多平台一致性成本。
2. **编辑器与引擎模板可替换**，适合形成主题、运行时和插件生态。
3. **素材管理、预览、脚本和导出在一个工作区**符合国内创作者预期。
4. **Web 直接发布**是试玩、分享、评审和正式发行的共同入口。

#### 需要超越

- 流程图不能停留在附加功能，必须与脚本 AST、诊断和运行状态真正统一。
- 手机端要有专门交互，而不是把桌面页面缩小。
- 团队协作、稳定工程 ID、资源去重、语义合并和大型项目导航需成为基础设施。
- 发布不应要求普通用户理解 Android Studio 或手工包装。

### 3.5 LetsGal Studio

#### 公开演示观察

B 站公开视频展示了典型专业工作区：

- 左侧游戏预览与项目/资源树；
- 中央大范围节点图；
- 右侧属性与参数区域；
- 底部日志/输出；
- 节点内可见图片预览和多个可编辑参数。

这说明国内用户对“Unity 类工作区 + 蓝图式故事编排 + 即时预览”有明确兴趣。

#### 必须实测的未知项

- 节点图是唯一数据源，还是能与文本双向编辑？
- 数万句对白时的性能、搜索、分组与版本控制方式；
- 自定义命令和插件 API；
- 运行时的存档兼容、回滚与本地化能力；
- Windows/Web/Android/iOS 导出和签名流程；
- 手机端编辑、协作、工程开放格式和许可。

在完成实测前，不能以“最完善”的视频标题代替产品结论。

### 3.6 Ren'Py

#### 已确认能力

- 可读 DSL 与 Python 扩展，长期用于商业视觉小说。
- 内建保存、读取、回滚、历史、Screen Language 和丰富显示系统。
- 支持 Windows、macOS、Linux、Android、iOS；WebAssembly/Web 仍有明确限制。
- 开发工具支持重载脚本、跳到当前语句和交互式检查。

#### 值得吸收

- **回滚是视觉小说核心语义**，状态系统从第一天就要为回滚设计。
- **UI 需要声明式语言/组件体系**，而不是只允许替换几张皮肤图。
- 开放脚本和运行时创造了庞大社区与长期可维护性。
- 工程必须允许高级开发者脱离可视化编辑器工作。

#### 需要超越

- 提供官方视觉路线图、时间线、舞台布局和移动端编辑。
- 在保留自由度的同时，让非程序用户不接触 Python。
- Web 构建需避免大运行时下载和浏览器兼容不确定性。

### 3.7 Visual Novel Maker 与 TyranoBuilder

#### 共同优势

- 拖拽命令、场景编辑和 Live Preview 对新手非常友好。
- 常见镜头、视频背景、Live2D、气泡和 UI 功能可快速使用。
- 桌面与 Web 发布路径清晰。
- 可通过脚本/扩展进入高级定制。

#### 共同短板

- 桌面优先，没有现代移动创作工作流。
- 命令列表和视觉块在长篇中容易重复、难搜索、难批量修改。
- 多人合并时，专有或大块工程文件不如分场景文本友好。
- TyranoBuilder 的移动发布还需要第三方包装，不能称为真正一键发布。

#### 值得吸收

- 新手模板、逐步教程和合理默认值；
- 演出命令的拖放与即时视觉反馈；
- “无代码起步、脚本突破上限”的渐进式能力；
- 发布中心对目标平台的清晰说明。

## 4. 扩展竞品启示

### 4.1 ink / Inky

ink 证明了“文本优先、逻辑嵌入文本”的语言可以支撑百万字级分支叙事。Inky 的边写边玩、错误高亮、跳转定义、JSON 中间格式和 Web 导出值得直接借鉴。

关键启示：**大型内容的真源应该是可读、可拆分、可编译的语义文件；图是导航和编辑视图，不应成为唯一存储方式。**

### 4.2 Twine

Twine 把 Passage 图和单 HTML 发布做到了极简，但社区反馈指出，当项目达到数千乃至上万 Passage 时，会需要章节/文件夹、资源管理、外部文本编辑和更强调试。

关键启示：

- 路线图必须支持分层、折叠、搜索、过滤和局部加载；
- Story Format 的可替换思想适合主题/运行时模板；
- 单文件分享适合原型，但正式工程需要目录化与版本控制。

### 4.3 Dialogic

Dialogic 同时提供可移动事件块、内部文本编辑器和外部文本编辑，说明视觉/文本双模式已成为现代叙事工具的合理预期。

### 4.4 GDevelop 与 Construct 3

它们证明：

- 手机和平板可以完成完整项目编辑，而不只是查看；
- 浏览器/PWA 能成为跨设备编辑基线；
- 本地文件 API、云项目和版本历史可以共存；
- Android/iOS/桌面构建服务能把 SDK 复杂度从终端设备移到云端；
- 手机 UI 必须单独优化，不能照搬桌面面板。

WorLd Studio 应吸收它们的跨设备基础设施，不复制通用游戏事件系统。

### 4.5 Kocho

Kocho 的价值在于验证了“只用手机制作视觉小说”的需求。其后续维护和导出能力不足也说明：移动端创作若没有开放工程格式、跨设备同步和独立发布链路，很容易变成封闭内容平台。

## 5. 用户痛点归纳

| 痛点 | 公开反馈/现象 | 设计响应 |
|---|---|---|
| 路线看不清 | 用户明确希望思维导图式路线追踪 | 两级路线图、结局路径高亮、当前状态模拟 |
| 节点图越做越乱 | Twine 大项目需要章节/文件夹；纯图难承载万行对白 | 全局图只放场景，内部用时间线/脚本 |
| 手机不能做完整项目 | Kocho/Intale 等消失后仍有持续需求 | 手机 Focus Mode、原生资源选择、云构建 |
| 可视化会锁定 | Ren'Py 用户希望导出干净 \`.rpy\` | 可读脚本、开放项目格式、无编辑器运行 |
| 逻辑错误发现太晚 | 用户需要不可达、无限循环、丢失引用校验 | 增量编译器 + 路线求解 + 发布门禁 |
| UI 定制很耗时 | B 站教程用大量章节处理标题、对话、存档、历史和设置 | 主题系统 + 可视化 UI Composer + 高级组件扩展 |
| 多语言与配音容易错位 | 成熟工具都引入稳定行 ID 和资源映射 | 文本 ID 永不随改名变化，翻译/配音按 ID 管理 |
| 视觉编辑和文本编辑互相破坏 | 移动拖拽失败时用户回到文本；不同工具格式不统一 | 单一 AST、所有视图发出语义命令 |
| 打包依赖本机 SDK | Android Studio、Xcode、第三方 wrapper 阻塞新手 | 隔离云构建、签名向导、可复现构建 |
| 团队文件冲突 | 表格/单文件/二进制工程难合并 | 分场景文本、稳定 ID、语义 Diff、锁与评论 |

## 6. 机会地图

### 必须达到的行业基线

- 对话、选择、变量、条件、跳转和自定义命令；
- ADV/NVL/气泡文本；
- 角色、表情、背景、CG、音频、视频、转场和摄像机；
- 保存/读取、快速保存、自动保存、回滚、历史、自动播放和跳过已读；
- 标题、设置、存档、鉴赏、音乐室和结局；
- 多语言、Ruby、CJK 禁则、字体回退、语音关联；
- Web、Windows、Android、iOS 发布；
- 可扩展 UI 和运行时 API。

### 真正的差异化

1. **四视图同源编辑**：路线图、时间线、文本、舞台。
2. **移动端完整创作**：不是伴侣应用。
3. **Narrative QA**：状态空间求解、路线覆盖、存档迁移检查。
4. **本地优先协作**：离线可用，联网后增量同步。
5. **无锁定发布**：工程和脚本可读，运行时可独立。
6. **构建即服务**：任何设备发起多平台、签名和商店发布。

## 7. 竞争策略

WorLd Studio 不应宣传“功能数量最多”，而应围绕三个可验证承诺：

- **写得快**：大量对白、批量资源和翻译工作不会被可视化操作拖慢。
- **看得懂**：非程序用户能看到路线、状态、演出和错误原因。
- **发得出**：同一工程在任何编辑设备上都能产生一致的多平台发布包。
