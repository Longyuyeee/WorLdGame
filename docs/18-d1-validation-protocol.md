# D1 用户验证协议

> 状态：Phase 0 候选协议，批准并完成原型后执行。
> 目标：用行为证据决定信息架构和交互是否成立，不用“看起来很酷”代替可用性。

## 1. 研究问题

1. 用户是否理解 Route、Sequence、Script、Stage 编辑的是同一内容？
2. 七种模式能否按任务被正确选择，而不是增加认知负担？
3. 新手是否能完成第一条可玩分支，专业用户是否仍能高速编辑？
4. 手机列表式路线与“连接到……”能否替代精确拖线？
5. 多彩语义是否提高定位速度，并在色弱/无颜色条件下保持可理解？
6. Full Motion 是否解释关系，Reduced Motion 是否保持全部功能？
7. QA、构建失败、Dicing建议和恢复流程是否可解释、可逆？
8. 原型与 WebGAL、Naninovel Story Editor 或可用同类完成相同任务时，效率和错误有什么差异？

## 2. 参与者

### 2.1 创作者组

至少 5 人：

- B类架构基准 3 人：长篇编剧、演出/技术美术、独立小团队制作人各至少1人；
- A类交互门槛 2 人：没有编程经验但有写作、同人或互动故事经验；
- 至少2人主要使用手机继续创作；
- 不招募参与原型设计的人作为正式样本。

### 2.2 玩家观感组

至少 5 人，完成校园 Benchmark 片段观感测试，重点评价文字、操作、演出、动效舒适度和附加页面完整性。创作者和玩家可以部分重叠，但两种角色的记录分开。

### 2.3 隐私与同意

- 参与者使用匿名 ID，如 `C01`、`P01`；
- 录屏、录音和引用原话分别取得同意；
- 不收集真实未公开剧本或私人项目；
- 测试工程只使用原创 Benchmark 内容；
- 原始录像设定保留期和访问人，报告只保留必要证据；
- 参与者可随时停止，不把停止视为失败。

## 3. 设备与环境

| 组别 | 环境 |
|---|---|
| Desktop | 1440×960 原型视口、键鼠；第二轮开启200%缩放/键盘路径 |
| Mobile | 393×852 原型视口、触控；模拟键盘、窄屏和安全区 |
| Motion | 同一任务分别运行 Full 与 Reduced，顺序交叉平衡 |
| Competitor | 同设备、同故事结构、同计时方法；无法实现的任务记录为“不支持”，不强行替代 |

真实目标机的性能结论属于 S0；D1 只评估交互、信息密度和主观舒适度。

## 4. 测试材料

- 校园 Benchmark Episode 的统一工程快照；
- 桌面/平板/手机可点击原型；
- 六组可播放动效与 Reduced 版本；
- 任务卡，不提前透露正确导航路径；
- 开场背景问卷与结束访谈；
- 观察记录表、事件时间线和严重度规则；
- WebGAL、Naninovel Story Editor 或可用同类的同任务准备工程；
- 测试后恢复到干净快照，避免前一位参与者状态污染。

## 5. 主任务

主持人只读任务，不提供路径提示。除非参与者明确放弃，否则不教学。

| ID | 任务 | 成功条件 | 目标时间 | 核心风险 |
|---|---|---|---:|---|
| T01 | 创建角色并写三句对白 | 角色、对白与预览一致，自动保存可见 | 4 min | 新手入口、连续录入 |
| T02 | 添加两个选项并连接不同结局 | Route显示两条有效路径 | 5 min | 四视图理解、拖线替代 |
| T03 | 找出不可达回收场景 | 能解释原因并定位条件 | 4 min | QA可解释性 |
| T04 | 在Script改角色名并检查Sequence | 引用安全更新且上下文不丢 | 3 min | 文本/图形同源 |
| T05 | 在手机替换立绘并移动角色 | Stage与命令同步，可用数值替代手势 | 5 min | 移动精度 |
| T06 | 从第二个选项直接预览 | 从指定语句运行，变量可见 | 3 min | 即时预览与定位 |
| T07 | 导出Web发布配置 | 通过校验并理解构建交接 | 5 min | 无云本地发布模型 |
| T08 | 找到变量由哪里修改 | 展示写入位置和受影响结局 | 4 min | 大型项目追踪 |
| T09 | 处理Dicing建议 | 理解收益/内存，应用后能回退 | 5 min | 自动优化信任 |
| T10 | 恢复误删内容 | 找到快照并恢复，不破坏新修改 | 4 min | 数据安全与恢复 |

通过标准不是所有人都在目标时间内完成；目标时间用于发现离群阻塞，不作为强迫参与者加速的压力提示。

## 6. 七种模式理解测试

向参与者展示七个模式名称、图标和一句场景描述，让其选择最适合模式：

- 快速写长对白 → Writer；
- 调整镜头和音画同步 → Director；
- 检查结局和分支 → Flow；
- 批量管理翻译/配音 → Production；
- 定位变量与不可达剧情 → Debug & QA；
- 在手机继续修改 → Mobile Focus；
- 第一次创建短篇 → Quick Start。

门槛：至少 6/7 首次选择正确；选择错误后能根据模式描述自我修正。若模式之间持续混淆，优先调整命名和信息架构，不增加教程遮罩掩盖问题。

## 7. 动效实验

### 7.1 设计

- 参与者随机先用 Full 或 Reduced；
- 完成 MOT-01、MOT-02、MOT-05 三个代表任务；
- 记录完成时间、误操作、是否等待动画、是否理解因果；
- 之后切换另一档重复不同内容的等价任务，避免记忆答案。

### 7.2 阻断条件

- 动画期间无法输入、保存、撤销或切换；
- Reduced 丢失状态、来源、方向或构建阶段信息；
- 参与者因大范围缩放、闪烁或视差出现明显不适；
- 动效导致超过20%的任务时间回退且没有理解收益；
- 当前语句在多个视图之间产生错误对应暗示。

## 8. 竞品对照

### 8.1 对照原则

- 使用相同任务和尽量相同的预置工程；
- 不把“产品不支持该任务”记成用户失败；
- 分开记录学习成本、操作次数、完成时间、错误、恢复路径和结果可解释性；
- 不复制竞品界面、术语、素材或受保护视觉表现；
- 对不同定位的工具只比较可比任务。

### 8.2 优先对照任务

| 任务 | WebGAL | Naninovel Story Editor | Utage/其他可用工具 |
|---|---|---|---|
| 写对白并预览 | 是 | 是 | 是 |
| 建立选择与结局 | 是 | 是 | 是 |
| 文本/可视化同源修改 | 部分/实测 | 是/实测 | 表格路径 |
| 手机继续编辑 | 实测 | 非核心 | 非核心 |
| 路线可达性解释 | 实测 | 实测 | 实测 |
| Dicing收益/回退 | 否或有限 | 非核心 | 机制参照 |
| 构建失败向导 | 实测 | Unity路径 | Unity路径 |

“实测”表示 D1 执行时必须记录版本、日期和证据，不把调研印象当作结果。

## 9. 指标

### 9.1 定量

| 指标 | D1退出门槛 |
|---|---|
| 无指导任务完成 | 每名创作者至少8/10；T01/T02/T05/T10无致命失败 |
| 四视图理解 | 5人中至少4人能正确解释同源关系 |
| 七模式识别 | 平均至少6/7 |
| 手机核心任务 | T05与T02移动路径无致命阻塞 |
| 不可逆操作 | 0次未警告的数据丢失或无法恢复 |
| 动效阻塞 | 0次因动画锁住输入 |
| Reduced功能差异 | 0项功能/信息缺失 |
| 严重可用性问题 | Severity 0/1均为0后才通过 |

### 9.2 定性

- 每任务 Single Ease Question（1–7）；
- 全流程信心评分（1–5）；
- 哪个颜色/形状代表何种语义的复述；
- “下一步会去哪里”的预期与实际；
- 对自动优化建议的信任理由，而非只问愿不愿使用；
- 动效舒适度、专业密度和视觉噪声的开放反馈。

## 10. 问题分级

| 等级 | 定义 | 处理 |
|---|---|---|
| Severity 0 | 数据丢失、错误发布、无法恢复或误导性安全状态 | 立即停止相关测试，修复后重测 |
| Severity 1 | 核心任务无法完成、四视图概念失效、手机致命阻塞 | D1不得通过 |
| Severity 2 | 可完成但需主持人提示、明显绕路或持续误解 | 修订并针对性重测 |
| Severity 3 | 文案、间距、视觉层级或轻微效率问题 | 进入改进清单并验证无回归 |

## 11. 证据记录

每位参与者输出：

- 匿名ID、角色画像和相关经验；
- 原型版本、Figma节点、设备和动效档位；
- 每任务开始/结束、完成状态、提示、误操作和问题编号；
- 关键路径录屏时间码；
- SEQ、信心和舒适度评分；
- 观察事实与研究者解释分栏记录；
- 测试后恢复结果；
- 同意范围和原始数据删除日期。

汇总报告输出：

- 任务完成矩阵与时间分布；
- 按模式、设备、用户类型和动效档位的差异；
- 竞品同任务对照；
- Severity 0–3问题及修复版本；
- 信息架构、Token、组件和工程契约的变更记录；
- D1退出门是否通过，以及未通过项的下一轮计划。

## 12. D1 退出判定

D1只有在以下条件全部成立时通过：

1. 至少5名目标创作者完成正式任务；
2. 8/10无指导门槛和四项核心任务门槛达到；
3. 四视图同源、七模式和手机路径没有Severity 0/1；
4. Full/Reduced动效均不阻塞输入且信息等价；
5. Benchmark Episode方案和商业评分表获批准；
6. 所有Severity 2修复后完成针对性重测；
7. 原型结论已经回写PRD、UX、工程契约和S0 Spike阈值；
8. 产品负责人批准进入S0。

D1通过仍不等于允许产品编码。S0全部通过后，还需要产品负责人再次明确发出“开始开发”指令。
