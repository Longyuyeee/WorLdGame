# N21 真人产品验收执行包

> 协议：`N21-HV-01`
> 当前状态：`pending-participant`
> 完成模型：任务结果与实际阻塞；不记录操作时间，不以耗时判定通过
> 权威协议：[`config/n21-human-validation-protocol.json`](../config/n21-human-validation-protocol.json)
> 权威记录：[`evidence/n21/human-validation.json`](../evidence/n21/human-validation.json)

## 1. 目的与不可替代边界

本执行包用于关闭 N21 唯一剩余产品门：一名未参与实现、不了解 WorLd Story Script 语法的真实非程序用户，能否仅根据任务目标完成最小 Writer/Sequence 创作、保存重开，并运行一条路线到结局。执行前必须先满足 N23 编辑器可运行流程前提，并等待功能开发与整体 UI 整理达到适合真人介入的阶段。

自动化、AI、开发者演示、远程代操作或事后补写结果都不能替代该证据。当前记录明确为 `pending-participant`；它只证明验收已经可执行，不证明 N21 通过。

仓库中不得记录姓名、邮箱、账号、录音或其他直接个人信息。参与者仅使用例如 `participant-01` 的匿名编号，并确认同意记录任务结果、求助和实际问题。

## 2. 参与者资格

执行前由主持人逐项确认：

- 没有为本项目提交代码、设计或测试脚本；
- 不熟悉 WorLd Story Script 语法；
- 不是本轮任务的主持人或记录人；
- 同意以匿名编号记录任务结果；
- 独立操作鼠标、键盘或触摸设备。

任一项不满足，本轮不得登记为有效 N21 真人验收。

## 3. 主持人规则

主持人可以朗读任务目标、记录参与者主动提出的问题、误操作和阻塞点，但不得：

- 操作编辑器、鼠标、键盘或触摸屏；
- 指出具体按钮、菜单位置或准确点击顺序；
- 解释脚本语法或直接修复参与者工程；
- 在失败后修改记录为通过。

参与者每次主动求助都计入 `helpRequestCount`，无论主持人是否回答。

## 4. 执行前检查

1. 使用准备验收的确切提交，双击仓库根目录 `start-n23-acceptance.cmd`，确认浏览器打开 `http://127.0.0.1:43123/`，并把完整 40 位提交写入 `sourceBaseRevision`；
2. 确认打开的是项目首页，没有预先创建任务工程，也没有打开示例工程；
3. 确认浏览器/桌面窗口可正常保存、关闭和重开；
4. 准备观察记录，在参与者首次操作前开始记录任务结果与问题；
5. 不向参与者展示开发文档、自动化测试或实现代码。

## 5. 冻结任务

主持人只能按顺序给出以下目标，不增加实现提示：

| ID | 参与者任务 | 完成判定 |
| --- | --- | --- |
| T01 | 创建一个新的空白故事工程并进入 Writer | 非示例工程，可进入 Writer |
| T02 | 创建至少一名角色，并加入至少一条由该角色说出的对白 | 角色存在，Writer/Script 中存在引用该角色的权威对白语句 |
| T03 | 加入一个包含两个选项的选择 | 两个选项均保存在权威脚本 |
| T04 | 创建并设置一个变量 | 变量存在且有一次类型正确的设置 |
| T05 | 使用条件让故事能够到达两个不同结局 | 条件与两个结局均存在，引用无错误 |
| T06 | 为故事加入一个背景和一条 BGM 演出指令 | 背景和 BGM 指令通过类型化资源引用保存 |
| T07 | 保存工程，关闭后重新打开并核对结果 | 文本、排序、选择、Inspector 数据和稳定 ID 保留 |
| T08 | 启动完整流程试玩，选择一条路线并到达结局 | 从入口启动，选择可交互，并显示对应结局名 |

发生无法继续、数据丢失或崩溃时，应如实登记 `fail`。查找时间长、反复尝试或理解困难记录为真实摩擦点，但不再用一个任意时限替代产品判断。失败不是无效数据；它必须进入缺陷修复和下一轮复测。

## 6. 必须记录的数据

结束时立即填写：

- 输入设备列表；
- 求助次数；
- 每个任务的 `pass`/`fail` 与简短观察；
- 所有阻塞点和误操作，不做美化；
- 主持人是否操作编辑器，合格运行必须为 `false`；
- 保存关闭重开后的五项保持结果；
- 最终工程导出快照及观察日志的仓库相对路径和 SHA-256。

观察日志至少包含当前任务、可见行为、参与者原话的简短释义和是否求助。不要记录操作时间，也不要写入直接个人信息。

## 7. 通过、失败与关闭规则

只有同时满足以下条件才能把记录写成 `pass`：

- 参与者资格与同意完整；
- T01–T08 全部通过；
- 主持人没有操作或精确指导；
- 保存关闭重开的五项检查全部通过；
- 最终工程和观察日志存在且 SHA-256 已登记；
- 同一变更中关闭全部 active `RA-N21-*` 例外，并更新 N21、需求矩阵和当前状态审计。

若任一任务或持久化检查失败，记录必须为 `fail`，风险例外保持 active，N21 保持验收中，创建缺陷并修复后使用新的匿名参与者或在明确记录学习效应的条件下复测。

## 8. 机器审计

运行：

```powershell
npm.cmd run audit:n21-human-validation
```

审计器会校验协议哈希、任务顺序、任务结果导向模型、参与者资格、主持人边界、所有任务结果、保存重开、产物哈希字段以及风险例外状态。它明确拒绝重新加入以操作时间作为通过代理的协议。当前预期输出是 `PASS` + `recordStatus: pending-participant`，含义是“待验收状态真实且边界完整”，不是产品通过。

N23-E1–E7 的可运行、创作、资源迁移、独立 HTML、五分钟内容量和验收启动工程门已经完成。2026-09-01 产品负责人取消了过早介入的探索操作，要求先继续功能开发和整体 UI 整理；因此当前仍保持 `0/1`，没有 T01 完成记录或计时记录。待产品负责人确认进入真人阶段后执行本包；N21 通过后再按 [`N23-PA-01`](121-n23-product-acceptance-execution-kit.md)执行两名非实现者验收。在此之前不得把任何开发者或自动化操作登记为真人通过。
