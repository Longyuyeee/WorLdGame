# 素材来源台账、公开署名与部署准备 · 2026-10-16

接续 `30dc2a3`（[#338](338-web-mobile-input-and-resume.md)）。先读取实际制作名单、发布检查、双格式导出、制作交付/恢复、工程保存及素材替换代码，并对齐 [#304](304-web-complete-gal-delivery.md) 的完整作品发布主线。本批补齐作者能实际操作的来源核对和交接流程，不新增剧情版本、不转做原生平台，也不以来源可追溯代替发行许可。

## 作者现在能完成的任务

1. 在“发布”的作品信息、生成游戏或试玩与部署页进入“许可与上线准备”，查看待处理数量，打开“核对素材来源”。
2. 按名称/ID 搜索，或只看待处理素材；逐项记录来源类型、来源事实、发行条件状态、内部依据、确认人/日期和准确公开署名。切换素材保留整份未应用草稿，Escape 不丢修改；可以明确应用或放弃。损坏/未来版本台账不被静默覆盖，明确重建后才替换。
3. 待确认或需替换的记录可以保存。选择“已记录确认依据”时，必须有明确来源、依据、确认人和有效日期；该状态只表示作者记录完整，**不是工具核实授权、所有权或许可合规**。不自动填姓名、日期、版权声明或许可。
4. 台账按稳定 Asset ID 和原文件 SHA-256 关联。不同 ID 即便共用同一文件也不继承依据；替换文件后显示“文件已更换，需重核”，禁用旧记录编辑，明确开始重核后清除旧依据/人/日期，旧来源与署名只留作参考。可以直接前往同一素材的替换入口，再返回原导出流程。
5. “需展示的公开署名”不会自动公开。点击“加入玩家致谢（仅此条）”才进入制作名单，可重复点击而不重复追加；要求的准确文字没有出现在玩家致谢中会提示缺口。只复制该条公开文字，不复制内部来源、证据路径或联系人；还可以在原制作名单弹窗检查/修改。
6. 下载本次工程的内部发布准备清单；生成制作交付包时，自动附带 `release/preparation.json` 和 `release/准备上线.txt`，与源工程、游戏一起列入 `delivery.json` 的大小/摘要清单。新浏览器从交付 ZIP 恢复即可继续逐素材核对，无需另找本机台账。

局部填写不会阻止作者继续导出本地验证游戏；生成前的实际文件检查仍负责缺失/大小/摘要等技术阻断。界面明确区分“故事与素材检查通过”和“许可/实际部署尚未验收”，不把本地导出当作公网发布。

## 同批修复与审计

实际 WebKit 接续检查中出现一次“应用台账后保存并返回首页”被拒绝，原数据未丢。检查发现元数据变更会把已有保存的 saving/autosaving 改回 dirty，过早开放保存/项目切换控件。新增受控保存测试在旧实现失败，修复后通过：旧事务未完成时继续保持保存状态；旧事务结束后，新元数据仍待保存，再保存最新工程才允许离开，不用旧快照冒充新稿已保存。

同时修正新表单的稳定可访问标签、素材列表行高；没有通过删保护来适配脚本。过程中的几类测试假设也已纠正：select/textarea 的隐式标签包含选项或原文；旋转后首帧的旧 dvh 不能当稳定布局；WebKit 填写后立即读取按钮状态/仅检查按钮可用不代表提交和保存已结束；素材替换的真实按钮为“更新此资源”。最终等待布局稳定及明确的已保存状态。

一次隐私断言误把运行时代码中用于排除台账的保留 key 字面量当成数据泄露；现检查实际 payload 不含台账，并检查作者内容没有进入玩家文件。一次 Windows 重写既有调试 HTML 返回 UNKNOWN，磁盘空间充足，原因未确认；改用每轮独立临时目录后完成验证，不把该环境错误说成产品修复。最近一次失败在 `browser-failure.json` / `failure.png` 保留，仅作过程记录；最终结果以 `browser-checks.json` 为准。
