# 连续演出推进与后台检查点 · 2026-10-16

接续 [#348](348-web-history-navigation-and-protection.md) 的实际工作区。处理用户点按下一句时经过多步演出、剧情检查点造成的等待，准备 1.7.10 Web 候选。

## 已开发

- Runtime 增加 `advanceRuntimeHistoryToPresentationV1`。一次公开调用先完整验证历史，再在同一个同步操作中依原顺序执行内部演出/检查点；到文字、选项、等待、待完成效果、屏障、结局或首个错误即停止。输入只交给第一步，每条新记录继续验证/哈希。下一次调用重新验证，没有跨调用验证缓存、宿主回调或异步信任复用。
- Player Core 按同一批步骤处理媒体 Host、场景回想入口和检查点。批结果只保留步骤元数据，不保留每一步整条历史的数组副本；默认 Core 仍提供原即时检查点存档，Web 显式选择延后生成。
- Web 到达检查点时保存精确的历史前缀；既有受控 Worker 使用相同公开序列化器完整核对后，才由槽位协调器写入。继续阅读不改变候选的时间点，多个检查点保持各自前缀；手动/快速/场景自动保存、检查点共用有序的计算和存储队列。
- 关闭页面或更换工程/存储上下文会取消计算，迟到结果不再发起物理写入；超时或写入失败保留旧槽位和当前剧情。已经开始的物理事务不冒充可撤销。Worker 缺失时仍走完整验证的同步兼容路径，该环境可能等待计算。
- 自动播放的延后候选只属于本次输出，宿主接管后不在 Core 中积累旧历史前缀；回退、读档和回想入口清空候选，重新开始保留 Web 的延后策略。

## 实际浏览器对照

同一合成作品从标题实际读到 240 条历史，先测普通单句推进，再执行 8 步内部文本框演出及一个检查点；立刻继续下一句，然后在存读档界面读取真实 IndexedDB 检查点，必须回到第 240 句。

基线冻结本轮开始时 Runtime 历史/导出、Core、PlayerShell 四份源码，含上两轮未提交改动，见 `evidence/web-checkpoint-responsiveness/baseline-sources.json`。两组均使用正式 Player 样式、原生 Worker 与 IndexedDB。

| 操作 | 基线 | 当前 |
| --- | --- | --- |
| 239 条历史后的普通单句推进 | 74.1 ms | 121.1 ms |
| 8 步演出＋检查点到下一句 | 396.1 ms | 191.9 ms |
| 同次演出推进 ≥50 ms 主线程任务 | 278 ms | 未观察到 |
| 同次演出推进最大心跳间隔 | 296.9 ms | 62.7 ms |

两组推进前后权威状态 hash、恢复正文与 250 条历史一致，页面错误为空；当前组三次前台计算均完成，最大活动线程 1、fallback/失败/取消为 0。检查点序列化也实际经过 Worker；随后读回的仍为早前检查点。

这是本机 Chromium 151 的一次受控观察。普通单句阶段本次变慢，**没有据此关闭普通推进问题**；此次消除的是重复内部步骤和同步检查点造成的长任务，不是整体流畅性结论。原始 `baseline.json`、`current.json` 与恢复截图均在同目录。没有强制 GC、伪造历史或实际手机/物理内存证明。
