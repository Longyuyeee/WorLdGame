# 长篇历史回退与后台内存保护 · 2026-10-16

接续 [#347](347-web-reading-smoothness-and-history.md) 的实际工作区。本轮处理“从历史中跳回较早段落会停顿”以及“内存保护仍在主线程整理整份记录”两条使用路径，交付 1.7.9 候选。完整剧情、素材与存档协议保持。

## 实际问题和修改

### 点击较早的历史记录

旧实现逐步调用公开 Back，每一步重新验证整条 History；合并已读/收藏进度时，还会重算全部 entry 的身份。120 条记录回到第 21 条时，实测出现约 1 秒主线程任务。

现在增加 `backRuntimeHistoryToCursorV1`：每次用户跳转先完整验证一次，再在同一个同步操作中按原顺序回退。每一步继续保留状态合并、补偿计划、不可逆边界及首个错误；每次新调用仍重新验证，没有跨调用缓存或异步复用验证结论。重置一个 checkpoint 的 Meta Progress 时，只需重新生成相邻两条链记录，其余 payload 和身份不变。

Player Core 依次执行原补偿/频道恢复计划，保留完整历史、已记录后续和归档。模型对照逐步公开 Back 的完整状态、保存字节、前进结果及媒体补偿；真实界面的回退状态和 Host 身份也与基线相同。

### 收到宿主内存保护请求

完整恢复记录的验证、序列化及历史整理提案进入已有自包含 Worker。主线程只有在原始完整记录成功写入独立恢复区、且当前仍是同一份游玩状态时，才应用较短的回滚窗口。当前句、原 Host/工程对象及正式槽位保持；较早记录仍可在只读归档中查看。

计算期间可以继续阅读。进度已经改变时不写入过期计算提案，也不收缩新进度；物理写入已经开始后的状态变化继续按原保护拒绝应用旧提案。超时、换工程或卸载会停止计算、释放 Worker 和 URL；已开始的物理 IO 保留在途保护。失败可重试。缺少 Worker 的宿主保留原完整校验回退，该环境仍可能等待同步计算。

返回提案只安装 History 与相同的播放重置，保持当前工程、舞台 Host 和回想对象的身份。正常独立恢复与内存保护共享在途限制，整理期间不重复排队恢复任务。

## 本机实际对照

使用同一 160 段专用作品，实际逐句读到 120 条、快速保存、从历史回退到第 21 条、快速读取，再调用公开宿主内存保护接口，最后刷新并显式恢复原 120 条完整历史。基线冻结了本轮开始时 6 份实际源码，包含上轮未提交改动，保存于 `evidence/web-history-navigation/baseline-sources.json`；两组均采用正式 Player 样式和原生 Worker/IndexedDB。

| 操作 | 基线 | 当前 |
| --- | --- | --- |
| 120→21 条历史跳转，总阶段 | 1,076.7 ms | 93.5 ms |
| 同次跳转 ≥50 ms 主线程任务 | 1,016 ms | 未观察到 |
| 同次跳转最大心跳间隔 | 1,023.9 ms | 49.9 ms |
| 内存保护，总阶段 | 100.1 ms | 116.5 ms |
| 内存保护 ≥50 ms 主线程任务 | 52 ms | 未观察到 |
| 内存保护最大心跳间隔 | 68.2 ms | 17.3 ms |

内存保护总耗时略增，后台完成计算让界面可以继续响应。回退前后状态/Host 身份两组逐项相同；保护后当前句和状态 hash 相同，回滚窗口 64 条、较早归档保留；刷新恢复得到原 120 条记录。当前组四次前台计算完成，fallback/失败/活动数均为 0。

这是本机 Chromium 151 的一次受控对照、无媒体合成文本作品；不作为统计性能、真实设备内存压力、实际大作品或所有旧长帧问题的验收。原始结果、两组截图在 `baseline.json`、`current.json` 和 `*-protected.png`。
