## 正文更新和恢复保护的顺序

普通推进仍使用原 Runtime、完整历史校验、规范编码和 SHA。后台恢复虽然在 Worker 内生成存档，发送整份历史的 `postMessage` 本身仍会同步复制；原来的 Promise 微任务可能在正文获得渲染机会前执行这一步。

受控的[后台恢复 Runner](../apps/player-shell/src/recovery-session-client.ts)只记住上次实际发送的同步耗时；达到 4ms 时才在可见页面[跨过两次帧回调](../apps/player-shell/src/recovery-paint-yield.ts)，给已提交的正文一次渲染机会，再发送完整输入。快速复制和首个尚无计时的任务保留立即执行；一次变慢可能影响下次选择，下一次快速结果会清除慢速信号，释放资源也会重置。4ms 是本轮调度预算，不是设备通用性能承诺。

没有降低复制量、改变线程协议、缓存状态或省略校验。计时 API 不可用、受限或返回非法值不影响保存。隐藏页面不等帧；等待中转为隐藏立即继续；帧回调受限时由 100ms 计时兜底。这是调度上限，不是忙碌主线程或后台系统挂起下的绝对完成时间保证，也不能把帧回调当作屏幕实际呈现的测量。

等待期间取消会清除帧、计时器与可见性监听，不创建迟到 Worker。暂停或压力释放发生在等待中时，原任务若仍有效会以一次性线程完成，不把新线程停放回已经释放的池。单个运行任务、IO 背压、只接续最新进度、旧工程／显式读档的代次保护及失败重试规则保持。

手动／快速保存、读取、压力保护和公开一次性序列化入口不增加这次等待；没有 Worker 或无帧 API 的宿主保留原兼容路径。独立恢复区仍只有实际校验与写入成功后才能记为安全，8 秒警告和 5 秒序列化超时不放宽。
